# Aria v5.27 engine audit and implementation plan

## Findings

- The entire app and data are embedded in `piano/index.html`, with local storage and no runtime dependencies. Preserve this distribution property.
- `seq`, `f`, `beats`, `steps`, `holds` and optionally `left`, `lf` are parallel arrays. `stepNotes` pairs one right pitch with one left pitch at the same index; `noteTiming` gives both one duration and one next-onset. A sustained bass under several melody notes, chord tones, a rest in one hand, multiple voices and ties cannot be represented faithfully. Array padding would introduce bogus strikes and note lengths.
- `scoreLayout`, `scoreGlyph`, `noteGlyph`, `scoreView`, `renderScore` and `renderStaticSheet` are indexed by these arrays, draw an unbarred exercise and cannot render a real piano score. Pitch spelling is inferred from MIDI and a global `flats` flag. The static sheet uses fixed columns, not measures. Fixed center playhead depends on `scoreTranslation`, `moveScore` and `animateScore` and should be retained.
- `playDemo` sounds `stepNotes` with a single shared hold. `accept`, `advanceTiming`, `releaseChecks`, `startPractice` and `syncKeyboard` likewise assume each index represents a new simultaneous attack. The existing mic detects monophonic pitches; it must never advertise chord/both-hand checking. BLE MIDI and multi-pointer touch already have note on/off mechanics worth retaining.
- Completion `complete`, `levelPassed`, `coursePassed`, `completionSummary`, `renderNav`, `nextLevelOrLesson` assume exactly three generated levels and save all under `aria-progress-v1` by lesson ID; current sections do not exist. `expandStudy`, generated `lessonLevels`, `installBaylorCurriculum`, `sequenceBeginnerTraining`, `reviseBeginnerCourse`, and generated miniature routes manufacture content. Some melody data explicitly says simplified rhythm, references only a site homepage and includes generated fingerings; it cannot be relabeled as faithful scores.
- `showBrief`, `renderLearnStep`, `handMoves`, `movementExplanation`, `curriculumGuide`, `renderLevels`, `fitViewport`, result actions and sheet copy assume the current data. Finger labels must not render blank bubbles, `undefined`, or invented instructional movement when source fingers are absent. Some CSS/layout logic is keyed to course/melody and exact three levels.
- Existing tests are Node VM scripts in `piano/tests`, with many assertions specific to old curriculum. They are useful regression evidence for devices, pitch detection, voice lifecycle, score center, timing and accessibility, but curriculum assertions need explicit replacement, not blind edits to make them pass. Browser preview historically unavailable; report that limitation and test an actual browser if available.

## Data contract and scope

Use only reviewed, licensed, precisely identified editions and explicit complete excerpts. One piece has stable source-specific ID, title, composer, original instrumentation, arrangement/arranger where applicable, source edition and exact link, rights/attribution, meter/key/tempo and a list of available variants. A variant has stable ID, honest Simple/Intermediate/Expert label only if independently sourced and appropriate; an original score is never embellished to manufacture an Expert. Each variant has explicit measure-aligned section boundaries and `scope` (`complete` or `excerpt` with exact measure range). No duplicated pseudo-phrases, fabricated accompaniments, guessed fingers, or claim of whole work for an excerpt. Distinguish whole *available score* from complete original work.

Represent notation as explicit events in integer ticks (e.g. 480 per quarter) to avoid float drift: `{id, measure, tick, duration, staff:'RH'|'LH', voice, type:'note'|'rest', pitches:[{midi,step,alter,octave,finger?,tieStart?,tieStop?}]}`. Chords contain pitches sharing onset/duration; independent voices use separate events. Preserve spelling, explicit rests, written duration, measures, time/key signatures and per-note sourced finger only. Ties are notation events and become one sounding duration; continuation is not a required new attack. Validate nonnegative ticks, valid pitches and positive durations, measure lengths/voices, links and section coverage, source consistency, ties, known notation values and nonempty score before exposing content. Explicitly reject unsupported ornaments, tuplets, repeats, multiple independent same-pitch overlapping ties etc. unless implemented and verified—never silently approximate or publish an incomplete score as playable. Source data should be embedded into the HTML at build time, with any local research/generation separate.

Derive a performance timeline by grouping distinct attacks at each absolute tick, maintaining per-note off times and splitting only for display when needed. Rests advance time without requiring user input. Section boundaries should fall at measure boundaries without orphaned tie continuation; reject or explicitly handle boundary-spanning ties. Whole mode uses the entire verified available variant. Hand filtering operates on events, not pitch range.

## Implementation sequence and affected functions

1. Install a reviewed embedded repertoire catalog and deterministic validation/normalization before initialization. Replace/retire generated course/melody installation and old catalog paths. Use stable versioned IDs and a new progress key; do not transfer old manufactured-level completion to a different work. Keep old saved data untouched. Build a single catalog/course view around actual works; replace exact-3 assumptions in `renderNav`, `renderLevels`, `completionSummary`, `coursePassed`, `nextIndex`, `openLesson`, `showBrief`, and relevant event handlers. Show exact source, scope, arrangement and fingering status. Variant selector lists only available sourced versions.
2. Introduce score/timeline helpers and a session `{variantId, range:'section'|'whole', sectionId, hand, attacks, pos}`; section and whole modes are explicit. Store completion as variant + scope + section + input/hand, with whole completion only for an actual full-range run. Completing all sections may show all sections complete but never automatically mark whole complete. RH-only/LH-only/mic/touch remain distinct. Section replay, next section and play all from results; previous/next at bottom beside Replay, disabled at boundaries and never silently wrapping. Transition/reset must cancel timers, demo audio, notes and input trackers before changing session.
3. Rewrite `scoreLayout`, `scoreGlyph`/`noteGlyph`, `scoreView`, `renderScore`, `sheetLayout`, `renderStaticSheet` for tick-positioned grand staff, barlines, meter/key, pitch spelling, chords, rests and ties; wrap static sheet only at measure boundaries. Associate glyphs with event/attack IDs. Keep `scoreTranslation`/`moveScore` fixed-center mechanism and adapt `scrollScore`, `animateScore`, `refreshScoreMotion`, `setScoreTimingCue`, `updateReadingTip` to tick positions. Long scores need sufficient spacing and escaped metadata. Verify every supported symbol; disallow data the renderer cannot present faithfully.
4. Rewrite `playDemo` to schedule each onset and off from the same canonical timeline, including silence and overlapping sustains; await the final release before transitioning, and cancel scheduled sounds on stop. Adapt `stepNotes`, `noteTiming`, `syncKeyboard`, `renderNotes`, `updateProgress`, `accept`, `advanceTiming`, `checkRelease`, `startPractice`, `complete`, reset and timers to attacks, per-note duration and scoped boundaries. Simultaneous chord notes form a set and advance once all required pitches arrive; do not require held bass to be struck again. Ensure early/late/release feedback applies to individual attacks, and repeated notes need an actual reattack. For mic require a selected monophonic hand/voice; explicitly disable polyphonic choices. On-screen multitouch and MIDI retain independent note off behavior. If timing cannot yet correctly grade overlapping parts, disable timing grading for those scores with honest copy rather than falsely scoring them, while retaining correct demo playback.
5. Replace `showBrief`, movement teaching and `renderLearnStep` copy with verified score-specific phrase guidance; optional finger hints only when provided by the edition. No derived fingerings. Preserve basic keyboard/setup help without implying source fingering or grading posture. Adapt viewport and quick controls for sections/variants and source details.

## Verification gates

- Validate every source/variant and every measure against source (pitch, spelling, duration, rests, ties, hands, chords, source fingering and scope); include at least one fixture with unequal RH/LH durations, staggered onsets, chord, rest, tie and no fingers. Source agent supplies edition-level evidence.
- Unit/VM: deterministic attack and sound scheduling; held bass never retriggers; rest produces no sound/no target; tie playback merges and no second strike; chord accepts in either order once; different durations release independently; mic refuses polyphonic modes; source/no-finger labels; section boundaries; replay/next/previous; section vs whole progress, reload, hand/input separation and no legacy progress falsely migrated; audio/timer cancellation; fixed center at start, note transitions and final segment; static and moving score match. Include invalid dataset rejection.
- Run relevant existing DSP, MIDI/replay, hold, timing, center, touch/quick controls and notation sizing tests and distinguish stale curriculum expectations from genuine regressions. Verify single HTML runs with network disabled and no external requests. Where a real browser is available, smoke test desktop and mobile-width layout, score legibility/overlap, keyboard, demo, sections, storage/reload and direct file download. BLE and microphone require real hardware/permissions and should be reported as unverified if unavailable; VM tests alone cannot establish hardware correctness.
